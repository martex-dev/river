# Security review — River 0.0.3

**Scope:** encrypted local database, key protection, passphrase flow,
migrations. Internal review; not an independent audit.

| Area               | Check                                                                                                                                                               | Result                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Data at rest       | Database file contains no plaintext and no SQLite header                                                                                                            | ✅ unit test with a marker string; e2e checks the header |
| Wrong key          | Opening with another key fails (`SQLITE_NOTADB` → error state, nothing overwritten)                                                                                 | ✅ unit test                                             |
| Key wrapping       | OS keystore via `safeStorage`; Linux `basic_text` fallback rejected (treated as no keystore)                                                                        | ✅ code review; Linux CI exercises the passphrase path   |
| Argon2id           | **Found:** Electron's BoringSSL lacks Argon2 although `crypto.argon2` exists and Node tests passed. Switched to libsodium; test asserts libsodium == OpenSSL output | ✅ fixed before release                                  |
| Passphrase sealing | AES-256-GCM with AAD; wrong passphrase and ciphertext tampering both fail closed                                                                                    | ✅ unit tests                                            |
| Online guessing    | Exponential delay after each wrong unlock via the UI (offline guessing bounded by Argon2id 64 MiB/3 passes)                                                         | ✅                                                       |
| Key handling       | Key buffers zeroed after use where possible; key never crosses IPC; passphrase only travels renderer → main once                                                    | ✅ code review                                           |
| Failure safety     | Damaged key file never overwritten; keyless database moved aside; locked keyring → error, data untouched                                                            | ✅ unit tests                                            |
| Migrations         | One transaction; encrypted backup before destructive steps; newer schema refused                                                                                    | ✅ unit tests                                            |

## Residual risks

- Passphrase mode: anyone with the files can attempt offline guessing; strength
  depends on the passphrase (minimum 10 characters, guidance shown).
- OS-keystore mode protects against other users and offline disk theft, but not
  against malware running as the same user (out of scope, THREAT_MODEL §4).
- JavaScript cannot guarantee secrets are wiped from memory (GC copies).
