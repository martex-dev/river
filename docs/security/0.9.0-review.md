# Security review — River 0.9.0 (pre-1.0 review)

Scope: everything added from 0.2.0 to 0.9.0 — communities, roles and
permissions, attachments, direct messages and groups (libsignal), community
key rotation, social posts and stories, backups, TURN, and the server routes
behind them. Method: code review of every IPC handler, every server route and
every place untrusted input is parsed or rendered; plus the automated tests
listed below. This is an internal review, not an independent audit.

## Findings fixed in this release

| Finding                                                                                                    | Fix                                                                                    |
| ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| A client could flood the realtime socket (typing/signal events fan out to other people)                    | Per-connection token bucket (40 events/s, burst 400); floods close the socket (`4429`) |
| A device that never collects mail lets senders fill the server's disk                                      | Mailbox cap per device (`RIVER_MAILBOX_LIMIT`, default 5000); further mail refused     |
| Unlimited uploads could fill the server's disk                                                             | Per-person storage quota (`RIVER_ATTACHMENT_QUOTA_MB`, default 2 GiB)                  |
| Prekeys from a previous install of a device stayed on the server, so a stranger's first message could fail | First upload from an install replaces all of that device's prekeys                     |
| Faint text failed WCAG AA contrast; channel rows nested a button inside a button                           | Contrast token raised to ≥ 4.5:1; rows restructured; axe-core audits added to e2e      |

## Checks

| Area                 | Check                                                                                                                                                                                        | Result                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| IPC                  | Every handler validates input with zod in main (`communityActionSchema`, `dmActionSchema`, `socialActionSchema`, attachment pointers, backup restore); trusted-sender check on every channel | ✅ code review; malformed-action tests                     |
| Renderer output      | No HTML injection: messages, names, captions render as text (React); RichText builds elements, never `innerHTML`; avatars must match a `data:image/(png\|jpeg\|webp)` pattern                | ✅ code review                                             |
| Received files       | Never opened automatically; only an allow-list of image/audio/video types render inline; save dialog uses a sanitised base name; programs carry a warning                                    | ✅ code review                                             |
| Attachment crypto    | Digest and MAC checked in constant time before decryption; local copies stay encrypted; key only in SQLCipher                                                                                | ✅ `attachment.test.ts`, integration tests                 |
| Direct messages      | libsignal unchanged; bundles checked against the identity-signed device list and against community-sealed identity keys; verified contacts block on key change                               | ✅ `session.test.ts`, `dm.test.ts` (incl. server key swap) |
| Message content      | All decrypted content parsed with zod; edits/deletes only from the author; group traffic only from members; posts only from accepted contacts; reactions/comments only from the audience     | ✅ integration tests incl. spoofing attempts               |
| Community keys       | Rotation on removal; keys accepted only for reached epochs and only if they open the sender's profile; key requests answered only with a join proof                                          | ✅ `epochs.test.ts` (incl. injected fake member)           |
| Server authorization | Every route requires a session; permissions and role hierarchy enforced server-side; non-members get "not found"                                                                             | ✅ `communities.test.ts`, `messaging.test.ts`              |
| Server abuse         | Rate limits per route, mailbox cap, storage quota, socket flood control, envelope and body size limits                                                                                       | ✅ tests                                                   |
| Backups              | AES-256-GCM under HKDF of a 128-bit secret; checksum words; restore only into a fresh install; sessions/prekeys excluded                                                                     | ✅ `backup.test.ts` (crypto and end-to-end)                |
| TURN                 | Short-lived credentials (6 h), coturn REST format, never long-lived secrets on clients                                                                                                       | ✅ test                                                    |
| Upgrades             | Local database upgrades from every released schema keep data                                                                                                                                 | ✅ `upgrades.test.ts`                                      |

## Residual risks (accepted for 1.0, documented to users)

- **Metadata**: the server sees who messages whom and when (no sealed sender),
  community membership, roles, timing and sizes. See THREAT_MODEL.md §5.
- **Community keys** are shared per epoch: anyone with a valid invite link can
  read the community; rotation protects only content sent after a removal.
- **Groups and posts** use pairwise sessions (fine for ≤ 32 members / a few
  hundred friends; sender keys would scale better).
- **Attachment IDs** are bearer tokens: any signed-in user who learns an ID can
  download the ciphertext (useless without the key from the message).
- **Single device per account**: multi-device linking moves to Stage 2; a backup
  is the way to move to a new computer.
- **No independent audit** yet, no Authenticode / Apple notarization.
